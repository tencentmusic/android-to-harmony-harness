# Agent 入口：联合评审与逐点验收

新迁移默认使用本入口。运行 `harness.py capabilities` 确认统一接口 `migration-harness/1`，合同协议为 `migration-harness/1`。
当前格式 run 由 `resume` 只读恢复并核对原审批与证据；概要与限制见 [README.md](README.md)。
统一使用 `python <包根>/scripts/harness.py`，文档命令以团队包根目录为当前目录。
本目录的文档、示例和适配器均随包提供，运行时不依赖发布者的源码仓库。

## 0. 续行与结束条件

开始准备前按 [会话协议](LIFECYCLE.md) 保存用户请求与范围；run 创建前使用 journal，创建后 attach。
恢复先读 `resume`，核对原进程与结果，再登记 session resume。最终答复前执行 `end-check`，
消费拒绝回执的 next_action；宿主 hook 的接入与能力边界以该协议为准。
通过 CLI/SDK 接入其他 Agent 或需要由 Harness 自动续行时，按 [通用运行器](AGENT-RUNNER.md) 配置
`agent-check/agent-drive`。托管子进程按请求中的 `next_action` 提交任务证据，由外层运行器执行结束检查；
`agent-status` 有未决调用时先 `agent-reconcile`，同一调用的进程与结果核对完成后再续接。

恢复会话、收到进度问题、批次执行结束或准备最终答复时，先读当前 run 的 `status` 和
`continuation`。`can_end_turn=false` 时执行 `next_action`，用 commentary 汇报进度，然后重新检查；
阶段性报告、构建成功、局部验收通过以及 `run --limit/--tasks/--points` 返回都不是完整迁移的结束条件。
用户问“做完了吗”“为什么停了”仍按原授权继续；用户明确暂停或限定只做局部检查时遵从实际请求。

按 `pending_actions` 先做 Agent 工作，再处理人工门禁。`blocked_tasks.root_task_ids` 定位依赖根因，
不要把 `blocked` 数量当成外部阻塞。`needs_diagnosis`、`input_missing` 和工具错误先检查并修复；
`in_doubt` 先核对进程、请求和已有结果，完整结果走 reconcile，禁止直接重放外部动作。
预算耗尽先记录诊断和新策略，再按预算协议处理；不能重置记录或无进展地反复重试。

仅在当前请求完成、用户明确暂停，或确需人/外部输入且全部独立工作已完成时结束本轮。
请求审核前先生成当前 HTML/最终报告，沿用已有有效批准；外部阻塞须列明实际检查证据、影响点及
需要的具体输入。当前协议不从错误文本推断外部 hold，`can_end_turn` 也不覆盖用户明确暂停。
`status/report/verify` 是检查和建议，不执行下一步、不启动后台任务；托管续行使用显式的 `agent-drive`，其余由当前 Agent 完成。
字段与分支见 [CONTRACT.md#续行建议](CONTRACT.md#续行建议)。

用户明确收窄交付验收范围时，完成该范围检查后继续做代码与证据复核、测试入口清理和交付报告。
使用 [限定范围收尾](CONTRACT.md#限定范围收尾) 的 `closeout prepare` 保存原话、逐项结果及其余点的排除清单；
先按 [开发交接](HANDOFF.md) 生成鸿蒙工程内的 HTML，并将其作为 closeout 的 report。呈现绑定当前源码、候选包和证据的最终 HTML，取得实际人工结论后
执行 `closeout decide`。`scoped_complete` 只代表用户限定范围交付，全量 `verify` 保持原有含义。

## 1. 查证并准备联合评审包

读取项目规范，确认分支、模块、宿主和 Android 来源。先查项目知识，再使用针对性的源码搜索、资源读取、设备观察与构建工具。
按 [CONTRACT.md](CONTRACT.md) 组织项目 Profile：模块、知识来源、工具用途、调用 argv；登记真实可用能力，不把未接入的工具当成已可调用。
工程首次接入或所需能力缺失时，按 [项目接入](PROJECT-EXECUTION.md) 验证适用构建、签名安装、HAP/HSP 测试和采集能力并保存收据。
新项目先用 project-discover 生成待核对配置，执行前读取 execution-plan 的 required/verified/missing，补齐所属任务的准备条件。
后续任务直接读取 Profile；仅对配置、工具或适配器变化影响的能力重新 project-verify，普通业务改动沿用工程接入结果。
动态设备与业务条件每轮观察，新候选包仍完成本次构建与实际验收。此接入在所属工程模块处理，沿用当前阶段顺序与审批门禁。

新任务先按 [测试计划生成](TEST-PLAN.md) 分析本次迁移变化和影响路径，再生成相关场景；确认
`capabilities.change_driven_test_plan=true`，使用 `plan` 编译合同。状态清单作为需求资料，场景按实现与失败风险分组，
验证方式逐项选择。先复用已有有效测试，补本次缺口；每个新增/替换/删除的行为及受影响的关键兼容行为均有覆盖。
完成条件：变化有来源、场景相关、同类消费者有分组依据，未纳入状态有适用性依据，报告能区分场景、断言和执行套件。

按触发路径记录页面、弹窗、加载、成功、失败、权限、退出、取消和身份/配置条件及 Android 来源。
仅为选中视觉检查的状态准备截图基准；无法到达时记录 baseline_gap，继续独立查证。实际范围收窄遵从用户原话；
未变化或未迁移状态可按源码/差异证据判定不适用。已有无 test_plan 的 run 保持原逐状态验收规则。

有视觉验收时按 [视觉取证与比较](VISUAL.md) 核对能力、采图和 `visual_comparison` 绑定。
正式 visual 必须执行内置比较并核验当前依赖截图；历史布尔结论不能代替本次图片比较。
原型与实现的人工核对单独留存；内置双图比较不自动证明三方一致或业务状态正确。

把需求、技术方案、UI 稿与验收点通过 state_id 关联。UI 稿包含对应关键状态，人工可查看的文件必须真实存在。
按 capability 划分评审域；需要独立补审时使用不同材料目录，将实际展示的图片、CSS、字体和附件固化进对应 bundle。
创建新合同和 run 后执行 context、review-packet，打开命令返回的 html_path，并把 HTML 文件链接作为联合审批入口交给用户。
完成条件：HTML 文件真实存在、材料和图片可查看，来源、状态、方案、UI、功能断言与视觉断言能逐项对应；待核实事项明确列出。
review-packet 同时保留 JSON；HTML 是材料快照，更新材料后重新生成并展示新入口，再收集绑定当前摘要的审核意见。

## 2. 一次联合审核，再实现

一次请用户审核需求、技术、UI，三项分别保存结论。只把用户对当前材料的实际意见登记到 approve，绑定 review-packet 的 input_digest 与原始批准证据。
用户允许升级工具，不等于批准业务功能的需求、技术或 UI；自动决定不能登记为人工批准。
awaiting_human 时继续可独立开展的查证与材料准备，待相关域批准后再修改对应业务 UI/逻辑。
完成条件：相关联合审核为 approved，对应 implement 任务为 agent_required。

实现入口、条件、数据、状态、最终动作、反馈和退出清理。遵守项目架构与资源规范，补齐测试适配器。
实现后对照实际 diff 校正测试计划：只补新增影响路径，合并等价检查或移除证实不适用的项，按 TEST-PLAN.md 留存版本与依据。
完成条件：diff 涉及的独立失败风险均被计划覆盖；执行前所选场景与当前实现一致。
变更涉及已审需求、方案、UI 或状态时更新材料，重新展示受影响域；未变更域的批准保持独立。
完成条件：用当前 input_digest 登记实现证据，任务与源码相符。

## 3. 批量运行，逐点诊断

run 连续执行多个验收点。每点分别提交功能或视觉观察、截图/日志与状态，不用任务级 passed 代替点级结果。
查看 coverage：操作经过和截图留存不等于断言通过。所有弹窗和中间状态都按已审清单核对，失败、未检查和受阻分别保留。

优先复用同一候选包与有效前置结果；同一路径的点合并到套件，减少重复导航；视觉任务可依赖设备任务并复用其当前包截图，独立做比较。
通过的套件仅读取结果摘要和覆盖映射；出现失败、缺断言或环境变化时再读取对应日志/图片。编译后的分组仍逐断言判定，
设备与视觉点的 covered_state_ids 必须由该次真实流程或有依据的代表消费者验证覆盖，不能复制其他状态的结果。
用条件等待代替无依据的固定等待。共享设备或账号的副作用操作串行，真实发布授权沿用用户在当前任务中明确给出的范围。
失败用 inspect 定位；必要时 retry 附诊断证据，run --tasks 仅运行受影响依赖闭包。
场景适配使用 [执行防护](PROJECT-EXECUTION.md#网络设备与检测器约束)：网络出口保留生产拦截器，检测器先跑正反例，设备动作使用新采集的语义目标与当前条件。
构建和测试生命周期使用已验证 recipe，查看显式包清单与每步收据；按 failure.category 恢复，不把工具异常当成业务失败。
可复用路径优先使用 [声明式套件](DEVICE-SUITES.md)；恢复 pending action 时先核对实际后置条件与诊断证据。
独立套件补验使用 run --points；先确认当前包、环境和前置状态，再按 [逐点恢复](CONTRACT.md#逐点恢复) 报告结果。
中断先核对进程和业务结果；已有完整结果时用 reconcile 接纳收据，完成条件是当前结果有效且没有重复执行业务动作。
准备重做外部动作或遇到预算耗尽时，按 [中断恢复与预算](CONTRACT.md#中断恢复与预算) 留存诊断与追加记录。

执行器报告 phase_seconds；查证、评审准备、等待、实现、诊断使用 timer 明确记录起止，不回填估算时间。
完成条件：每点有可复核结论；相关结果与当前源码、基准和候选包一致。发现漏项先 revise 扩充合同及评审，再继续验证。

## 4. 最终复核与交付

Agent 核对完整状态清单、diff、断言和原始证据，处理跨场景状态、回流、账号隔离及生命周期问题；review 必须覆盖全部 acceptance_ids 且 findings 为空。
按 [开发交接](HANDOFF.md) 完成适用的知识回灌及依据记录，再执行 handoff，将面向开发者的自包含 HTML
放到本次鸿蒙产品的 DevEco 工程 `androidtoharmonyharnessdoc/`。正文先给总体情况和未完成项，再展开需求、技术、UI、代码及接手信息。
report 保留执行诊断用途。打开并核对交接 HTML，取得针对当前候选与证据的最终人工结论，再登记 final approve。
完成条件：真实模式 verify 返回 delivery_ready、developer_handoff 为 current 且 continuation 无 Agent 待办。
未达到时按续行判断处理剩余点；允许结束的具体条件见 §0。
demo_only 和局部 passed 均不能表述为业务迁移完成。

经验证的适配器与知识结论按项目知识规范沉淀，无法适用时记录原因。外部评分接入、工具边界和共建评测见 [EXTENSIONS.md](EXTENSIONS.md)，评分不覆盖必验缺口。
