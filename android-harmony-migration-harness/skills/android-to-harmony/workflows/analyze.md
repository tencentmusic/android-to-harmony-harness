# Analysis-Only：Android 业务梳理

## 目标

产出一个“不打开 Android 工程也能用于鸿蒙施工”的事实文档。默认不完成目标架构设计。

## 1. 确定范围和格式

- 类名、文件、包或模块：按整个类，使用五块模板。
- 功能、场景、“从……到……”：按单一功能，使用六块模板。
- 拿不准时默认整个类。
- 入口页、聚合页、播放页、直播间或持有多个子业务的类：先扫描完整业务闭包；必要时按
  “总览 + 若干五/六块子文档”拆分，不能只写入口壳。总览也使用整个类五块模板，
  不另造七块或无约束格式；子文档按对象类型使用五块或六块。

## 2. 读取证据

按以下顺序搜索并记录证据：

1. 目标类、父类/接口和直接调用方。
2. 布局、点击入口、列表项、弹窗、子页面、Controller/Delegate/Adapter 等业务角色。
3. 协议、实体、接口 URL、请求参数、响应字段、错误分支。
4. 常量、枚举、页面参数 key、CMD、状态码的定义和值。
5. drawable、shape、selector、gradient、颜色、文案、动画和换肤入口。
6. 目标 Harmony 工程的同类实现，仅用于确认项目术语和已有能力，不反推 Android 行为。

Android 证据按 `../references/android-codegraph.md` 执行“CodeGraph 发现 → 远端精读 → 当前本地 HEAD
复核”；工具不可用、未索引或不可信时使用本地 `rg/git`。Harmony 始终使用当前工作树的本地
`rg/git`，不能通过 Android 图谱反推。找不到定义时写明“未找到定义 + 搜索范围 + 人工确认点”，
禁止猜值。

## 3. 形成业务闭包

至少覆盖：

- 用户可见入口和触发条件。
- 初始化、主流程、成功/失败/空数据/权限/登录等分支。
- 接口、Socket、缓存、页面参数和配置数据来源。
- 弹窗、二级页、列表项类型、回调回流和最终 UI 更新。
- 跳转目标、参数 key、默认值和结果回传。
- 本地资源真实名称、尺寸/颜色/圆角/渐变/selector 状态和换肤来源。

正文使用业务语言。Android 类名仅在标题、首次出现或证据定位处保留；不要用生命周期名或控件名
代替业务解释。

## 4. 写入 Markdown

- 整个类：复制 `templates/whole-class.md` 并填满五块。
- 单一功能：复制 `templates/single-feature.md` 并填满六块。
- 文件名：`梳理结果-<类名或功能名>.md`。
- 目录：当前 profile 的 `analysis_output_dir`；用户指定目录时以用户为准。
- 无接口、无资源或无某类数据时，仍保留主标题并写“无 + 已检查范围”，不要删块。
- 资源规格表放在最相关的主块内，不额外制造第七块。
- 默认只记录资源，不复制或打包资源；用户明确要求资源包时再执行。
- 完整功能 Harness 若判定存在用户可见 UI，`UI Layout Spec`、视觉原型和人工审核记录作为独立的
  UI Review 包输出，不增加五/六块业务事实文档的主标题；Analysis-Only 可以在
  生成当前需求、技术与 UI 的联合评审材料，取得对应实际决定后进入 ArkUI 实现。

## 5. 禁止默认输出架构设计

只梳理时可以客观描述“Android 当前业务角色如何协作”，但不得主动给出：

- Model/ViewModel/View 文件规划；
- 状态 owner、装饰器或 V1/V2 迁移方案；
- 目标目录树或组件拆分方案；
- “应该重构为……”之类目标架构结论。

用户明确要求架构方案时，先完成五/六块事实文档，再追加独立的“架构设计（用户要求）”部分，
并读取官方 MVVM 参考。

## 6. 交付前检查

- 主标题数量、名称和顺序与模板一致。
- 端到端流程包含入口、异步边界、成功/失败分支、UI/跳转/回流。
- 接口有完整 URL、方法、参数来源、返回字段和错误处理；未知项有证据范围。
- 常量同时写“名称 = 具体值”；没有静默保留符号名。
- 资源不是笼统的“图标/背景”，而是可定位的真实规格。
- 没有未经要求的 MVVM/目录/状态架构设计。
- 文件已实际写入配置目录。
